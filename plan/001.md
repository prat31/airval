## 0. Decisions captured

| Topic | Decision |
|---|---|
| Backend | Go, a single CGO-free binary with the UI embedded |
| Frontend | React + TS + Vite + Tailwind v4 + Radix + TanStack + ECharts |
| Targets | HTTP/REST, LLM provider APIs, RAG/agents/tool calls, multi-turn chat (all in v1) |
| Auth | Multi-user, organizations, RBAC, API keys; OIDC SSO in `ee/` |
| Storage | SQLite (all-in-one) + Postgres (production) |
| Execution | Separate `server` and `worker` processes over **NATS JetStream**; JetStream embedded in `airval dev` |
| Evaluators | Deterministic built-ins, LLM-as-judge (BYO keys), human review. *Custom code evaluators deferred to plan 002.* |
| Aesthetic | "Calm precision": cool slate neutrals, iris (indigo-violet) accent, light + dark |
| License | Open core: Apache-2.0 core, `ee/` under a commercial license |
| Name | `airval` · module `github.com/airval/airval` · image `ghcr.io/airval/airval` |

**Why NATS over Redis:** it's written in Go and can be embedded in-process, so `airval dev` stays a single binary with
zero dependencies. JetStream gives durable work queues, consumer acks/redelivery and key-value storage (for rate-limit and
lease state), and it streams progress events to the server for live UI.

## 2. Architecture

```
            ┌──────────────── airval server ─────────────────┐
 Browser ──▶│ HTTP API (chi, OpenAPI) · SSE live updates      │
 CI/CLI  ──▶│ Auth/RBAC · Scheduler (leader-elected via NATS KV)│
 Webhooks ─▶│ Run planner → publishes shard jobs              │
            │ Event consumer → SSE fan-out                    │
            │ Embedded SPA (go:embed web/dist)                │
            └───────┬───────────────────────────┬────────────┘
                    │ Postgres (pgx)            │ NATS JetStream
                    ▼                           ▼
            ┌──────────────┐         ┌───────────────────────────────┐
            │  Postgres    │◀────────│ airval worker (N replicas)     │
            │  (or SQLite) │  batched│ shard consumer → target adapter│
            └──────────────┘  writes │ → evaluator pipeline → results │
                                     │ judge pool · rate limiter · cache│
                                     └───────────────────────────────┘
```

**Binary subcommands**
- `airval dev`: all-in-one. Server, worker pool, embedded NATS, SQLite at `./airval-data`. Opens the browser. Zero config.
- `airval server`: API, UI, scheduler and planner. Stateless and horizontally scalable.
- `airval worker`: executes jobs. Scales horizontally; HPA (CPU) or KEDA (JetStream consumer lag).
- `airval migrate up|down|status`.
- `airval run --suite <id|slug> --target <id> [--wait] [--gate]`: CI client. Streams progress, prints a summary, exits 1 if the gate fails. Can also output JUnit XML or Markdown for PR comments.
- `airval version`, `airval config print`.

**Config:** a YAML file plus `AIRVAL_*` env overrides (koanf). Main keys: `database.url`, `nats.url` (empty = embedded), `secrets.master_key`, `server.base_url`, `auth.*`, `workers.concurrency`, `telemetry.*`.

## 3. Execution engine (the speed story)

### 3.1 Run lifecycle
1. **Plan.** The server resolves the suite (target config version, dataset version, evaluators, trials) and creates the `run`
   row. It splits examples into **shards** of about 25–100 (adaptive by dataset size) and publishes one JetStream message per shard
   to `runs.jobs` (WorkQueue retention). The run moves `queued → running`.
2. **Execute.** Workers pull shards. Each example × trial goes through the pipeline below.
3. **Ingest.** Workers buffer results and flush every 250 ms or every 200 rows: Postgres `COPY` / multi-row insert, SQLite batched tx.
   Per-shard progress counters are published to `runs.events.<runID>`.
4. **Finalize.** When the last shard acks, a finalizer (any worker, guarded by a KV lease) computes aggregates
   (means, percentiles, pass rates, per-tag slices, cost), evaluates gates, writes `run_summary` and fires notifications/webhooks.
5. **Cancel/retry.** Cancel sets a KV flag that workers check between examples. Failed examples can be retried in place:
   "Re-run failed" creates a child run that only covers the failed examples.

### 3.2 Per-example pipeline
`render request → call target (streaming if supported) → extract output/context/tool calls/usage → deterministic evaluators
→ LLM-judge evaluators (parallel) → persist`

### 3.3 Efficiency techniques (all v1)
- **Bounded, adaptive concurrency per target.** Each target has `max_concurrency`, `rpm` and `tpm` limits. A distributed
  token bucket lives in NATS KV, with local leasing of 1-second budget slices so workers don't hit KV per request. **AIMD**: back off on 429/5xx and
  `Retry-After`, ramp up on success. Total throughput stays near the target's real limit without errors.
- **Separate judge pool.** LLM-judge calls have their own concurrency and rate limits per provider key, so slow
  judges don't block target calls (pipelined stages over buffered channels).
- **Response cache.** Results are keyed by `sha256(target_config_version + rendered_request)`. Off by default for targets and on by default
  for judges (`sha256(judge model + prompt + output)`). Re-evaluating an old run with new evaluators costs **zero**
  target calls (the "Re-score run" action).
- **Short-circuit.** Optional `fail_fast` per evaluator: if a deterministic check fails, skip expensive judges for that example.
- **Early stop.** The gate can define a failure budget (e.g. stop after 50 critical failures) to cancel doomed CI runs early.
- **Sampling.** Run on a random or stratified (by tag) sample of N or X%. Great for fast PR checks, with a full run nightly.
- **HTTP/2 + keep-alive pools** per target host. Request bodies come from pre-compiled templates; no reflection in hot loops.
- **Batched DB writes**, plus large output text stored compressed (zstd) above 8 KB.
- **Provider batch APIs (opt-in).** For huge offline judge workloads (OpenAI/Anthropic batch, about 50% cheaper), mark as "slow mode".
- **Streaming everywhere.** Results show up in the UI live through SSE. Time-to-first-token is recorded as a metric.

### 3.4 Benchmarks as acceptance criteria
- With a mock target (10 ms latency, no rate limit), 1 worker × 256 concurrency: **≥ 5,000 examples/min** end to end, including
  3 deterministic evaluators and persistence on Postgres.
- Overhead per example (excluding target and judge time): **< 2 ms p95**.
- `make bench` runs these benchmarks; CI fails on a >15% regression.

## 4. Targets (adapters)

Each target has a `kind`, a `config` (JSON, versioned on every edit) and secret references.

| Kind | Notes |
|---|---|
| `http` | Method, URL, headers and body as templates (`{{ .input.question }}`, `{{ secret "KEY" }}`). Response mapping by **JSONPath** for `output`, `context[]`, `tool_calls[]`, `usage`, `cost`. Supports SSE/NDJSON streaming responses, timeouts, retries and mTLS. |
| `openai` | Any OpenAI-compatible API (OpenAI, Azure OpenAI, Ollama, vLLM, LM Studio, Together, Groq…). Chat + tools + JSON mode. |
| `anthropic` | Messages API, tools, system prompt. |
| `bedrock`, `vertex` | Via SDKs; credentials as secrets. |
| `agent` (http variant) | Same as `http`, plus mapping of an intermediate **trace** (steps, tool calls, retrieved docs) from the response. |

**Multi-turn:** an example may contain a `conversation` (a scripted list of user turns) or a `simulation`
(user persona prompt + goal + `max_turns` + stop condition). The adapter keeps state between turns (messages array, or a session
id extracted via JSONPath and fed back). Evaluators can score per turn or per conversation.

**"Test connection"** on the target form sends one sample example and shows the raw request/response with the mapping applied.
This is key to a smooth setup.

## 5. Datasets

- Import from **CSV, JSONL, JSON or Parquet**, paste, or **HF Datasets** (public, by repo id). There's a column-mapping step
  (input / expected / context / metadata / tags) with a preview.
- Spreadsheet-like editor (virtualized) for inline edits, bulk tagging, search and filters.
- **Versions:** edits accumulate as a draft, and "Publish version" freezes it (copy-on-write: a version is a list of example
  revision ids, so unchanged examples aren't copied). Suites pin either a version or "latest".
- **Add from run:** promote any run result (for example a failure) into a dataset as an example. This closes the loop.
- **Synthetic generation (LLM):** generate N examples from a description or seed examples. Off by default, uses BYO key.
- Export as CSV/JSONL.

## 6. Evaluators

All evaluators return `Score{value float64 (0..1) | nil, label string, passed *bool, reason string, meta json}`.
A suite attaches evaluators with a **weight**, **threshold** (pass if value ≥ t), **severity** (`critical|major|minor`)
and **apply-to** (final output, per turn, conversation, trace).

**Deterministic (pure Go, microseconds):**
`equals`, `contains` (any/all/none, case options), `regex`, `starts_with`/`ends_with`, `is_json`, `json_schema`,
`jsonpath_equals`, `numeric_close`, `levenshtein`, `rouge_l`, `bleu`, `length` (chars/tokens), `latency_ms`,
`cost_usd`, `tokens`, `tool_called` (name, args subset match, order), `tool_sequence`, `no_pii` (regex pack),
`refusal` (heuristic phrases).

**Model-based (BYO keys via secrets):**
- `embedding_similarity` (cosine vs expected; provider embeddings, cached).
- `llm_rubric`: custom rubric prompt, G-Eval style (CoT + score). Uses logprob-weighted scores when the provider supports it.
- Presets: `correctness` (vs expected), `faithfulness` / `groundedness` (output vs context), `answer_relevance`,
  `context_relevance`, `context_recall`, `hallucination`, `toxicity`, `bias`, `conciseness`, `helpfulness`,
  `conversation_goal_completion`, `conversation_coherence`, `tool_use_correctness`.
- `pairwise`: compares against the baseline run's output (win/tie/loss), with position-swap to remove order bias.
- Judges support **N-sample voting** (median/majority) for stability. Judge prompts are versioned and shown to users.

**Human:** a `human` evaluator puts results into a **Review Queue** (all results, failures only, or a sampled %). Reviewers
grade with keyboard shortcuts (1–5, P/F, labels, comments). Human scores can **calibrate** LLM judges, and agreement
(Cohen's κ) is shown on the evaluator page.

## 7. Suites, gates, triggers

- **Suite** = name, project, target(s) (one run per target; selecting several gives an automatic comparison), dataset
  version(s), evaluators (+ thresholds), `trials` (1–10), sampling, concurrency overrides, cache policy, baseline policy
  (`pinned run` | `last passing run on target X` | `none`).
- **Gate** = expression list: `mean(faithfulness) >= 0.85`, `pass_rate(all) >= 0.95`, `count(critical_fail) == 0`,
  `p95(latency_ms) < 2000`, `regression_vs_baseline(correctness) > -0.02`. They're built in a visual builder, stored as AST, and shown
  as human-readable text.
- **Triggers:**
  - *Manual*: "Run" button, with options (target, sample, trials, label).
  - *Schedule*: cron and timezone. The scheduler runs on a server leader elected via NATS KV lease.
  - *Webhook*: unique URL + HMAC secret. Payload fields can override `target` config variables (e.g. a deploy preview
    URL) and labels (`git_sha`, `branch`). They map naturally to GitHub/GitLab/Vercel deploy events.
  - *API/CI*: `POST /v1/runs` with an API key, or the `airval run` CLI. A GitHub Action wraps the CLI and posts a
    Markdown summary comment.
- **Notifications** (on run finish / gate fail): Slack incoming webhook, generic outgoing webhook, email (SMTP).

## 8. Data model (core tables)

All ids are UUIDv7 (time-sortable). Every row has `created_at`; mutable rows also have `updated_at`. Every project-scoped
row carries `org_id` and `project_id` for cheap authorization filtering.

```
organizations(id, name, slug)
users(id, email, name, password_hash?, avatar_url)
memberships(org_id, user_id, role)                      -- owner|admin|editor|viewer
api_keys(id, org_id, project_id?, name, prefix, hash, role, last_used_at, expires_at)
sessions(id, user_id, expires_at, …)
projects(id, org_id, name, slug, description, color, icon)
secrets(id, org_id, project_id?, name, ciphertext, nonce, key_version)
targets(id, project_id, name, kind, current_version_id)
target_versions(id, target_id, config jsonb, created_by)
datasets(id, project_id, name, description, schema jsonb, latest_version_id)
examples(id, dataset_id, revision_id)                   -- stable logical id
example_revisions(id, example_id, input, expected, context, metadata, tags[], conversation, created_at)
dataset_versions(id, dataset_id, number, note, example_revision_ids)  -- or join table dataset_version_items
evaluators(id, project_id, name, kind, config jsonb, version)   -- reusable definitions
suites(id, project_id, name, slug, description, config jsonb)  -- targets, datasets, evaluators+thresholds, trials, sampling
gates(id, suite_id, expr jsonb)
triggers(id, suite_id, kind, config jsonb, enabled, secret_hash?, next_fire_at)
runs(id, project_id, suite_id, target_version_id, dataset_version_id, trigger_kind, trigger_ref, labels jsonb,
     status, total, completed, failed, errored, started_at, finished_at, baseline_run_id, parent_run_id,
     gate_passed, summary jsonb, cost_usd, created_by)
results(id, run_id, example_id, example_revision_id, trial, status, output text/zstd, trace jsonb,
        latency_ms, ttft_ms, tokens_in, tokens_out, cost_usd, error, cached bool, created_at)
scores(result_id, evaluator_id, value, label, passed, reason, meta jsonb, latency_ms, cost_usd)
run_aggregates(run_id, evaluator_id, slice_key, n, mean, p50, p90, p95, p99, stddev, pass_rate, histogram jsonb)
review_items(id, run_id, result_id, queue_id, status, assigned_to)
annotations(id, result_id, user_id, evaluator_id?, value, label, comment)
comparisons(id, project_id, run_ids[], created_by)      -- saved views
notification_channels(id, org_id, kind, config)
audit_log(id, org_id, actor, action, target, diff, at)  -- ee
cache_entries(key, value bytes, created_at, expires_at)  -- or NATS object store; Postgres default
```

Indexes: `results(run_id, status)`, `scores(evaluator_id, result_id)`, `runs(suite_id, created_at desc)`,
`runs(project_id, created_at desc)`. Postgres partitions `results`/`scores` by month after 10M rows (migration-ready, not
on by default). Retention policy is configurable per project.

**Store layer:** `internal/store` defines interfaces. `internal/store/postgres` and `internal/store/sqlite` are generated by
`sqlc` from per-dialect `queries/*.sql`. A shared contract test suite runs against both.

## 10. Auth, RBAC, security

- Local accounts (argon2id) with secure cookie sessions (`SameSite=Lax`, CSRF token on mutations).
- First boot: if no users exist, `/setup` creates the owner + organization. The `AIRVAL_BOOTSTRAP_ADMIN_*` env vars do the same for Helm.
- Roles: **owner** (billing/org delete), **admin** (members, secrets, keys), **editor** (create/edit/run), **viewer** (read).
  Project-level overrides are an `ee` feature.
- API keys: `airv_` prefix plus a random value. Only the SHA-256 hash is stored. Keys are scoped to an org or project with a role.
- Secrets: AES-256-GCM with `AIRVAL_SECRETS_MASTER_KEY` (32 bytes, base64). `key_version` enables rotation (`airval secrets rotate`).
  Values are write-only via the API and decrypted only inside workers at request time.
- Webhooks: HMAC-SHA256 signature header plus timestamp, with a 5-minute replay window.
- SSRF guard for `http` targets: an optional allow/deny CIDR list (blocks metadata IPs by default).
- **ee/**: OIDC/SAML SSO, SCIM, custom roles and per-project RBAC, audit log, data retention policies, white-labeling.

## 11. UI / UX

### 11.1 Information architecture
Left **sidebar** (collapsible): org switcher → project switcher → sections:
`Overview · Runs · Suites · Datasets · Targets · Evaluators · Review · Settings`.
Top bar: breadcrumbs, a global **⌘K command palette** (jump to anything, "Run suite…", "New dataset…"), live run
indicator, theme toggle, user menu.

### 11.2 Key screens
1. **Onboarding / Setup wizard.** Create the project → add a target (with live "Test connection") → import or generate a dataset →
   pick evaluator presets → first run. Takes under 3 minutes. A **sample project** (mock target + demo dataset) can be loaded with one click.
2. **Project Overview.** Stat tiles (runs in the last 7 days, latest pass rate with delta vs the previous run, avg score, spend), a **trend
   chart** (pass rate per suite over time), recent runs list, failing gates callout.
3. **Runs list.** Table with status pill, suite, target, trigger icon, pass rate bar, key score, duration, cost and labels
   (git sha). Filters sit in one row above it. Multi-select → "Compare".
4. **Run detail** (the hero screen):
   - Header: status, gate verdict (with each gate expression ✓/✗), duration, throughput, cost, tokens, trigger, baseline link.
   - Live progress bar + streaming results while running.
   - **Scorecard row:** one tile per evaluator (mean, pass rate, delta vs baseline, sparkline of the last 10 runs).
   - Charts: **score distribution** histogram per evaluator; **latency** distribution with p50/p95/p99 markers;
     **pass-rate by tag** (horizontal bars); **evaluator × tag heatmap** (sequential iris); **cost/tokens** breakdown.
   - **Results table** (virtualized, 100k rows smooth): input preview, output preview, per-evaluator score chips, latency,
     status. Filter by failed/evaluator/tag/score range, plus full-text search.
   - **Result drawer:** input, expected and output side by side (with diff toggle), retrieved context, tool-call/trace
     timeline, each score with the judge's reasoning, raw request/response, and actions: *Add to dataset*, *Send to review*,
     *Copy as cURL*.
5. **Comparison.** Choose 2–4 runs. Shows a scorecard delta table, a **regressions / improvements** list (examples whose score
   dropped/rose most), a **scatter** of per-example score (A vs B; points below the diagonal are regressions), an aligned
   side-by-side outputs view and a pairwise win-rate bar.
6. **Suite detail.** Config summary, gates, triggers (cron preview "next 5 fires", webhook URL + copy + sample cURL), a
   history trend per evaluator, and a "Run now" split button.
7. **Suite editor.** A stepper (Target → Data → Evaluators → Gates → Execution) with an always-visible summary panel showing
   the estimated cost and duration for the run (from dataset size, cached-hit ratio and historical latency).
8. **Dataset detail.** Version selector, spreadsheet editor, column stats, tag cloud, import/export, diff between versions.
9. **Target detail.** Config editor with request/response mapping playground, version history (diff) and health (recent
   latency/error rate).
10. **Evaluators.** Library of presets plus custom evaluators. The editor has a **live preview** (paste output → see score + reasoning)
    and shows agreement with human annotations.
11. **Review.** Queue with a focused single-item view, keyboard-first grading, and progress.
12. **Settings.** Org, members, API keys, secrets, notification channels, appearance.

### 11.3 UX principles
- Keyboard-first: ⌘K, `j/k` in tables, `g r` (runs), `g d` (datasets), `?` for the shortcut sheet.
- Optimistic updates. Skeleton loaders that match the final layout. Every empty state has a primary action and an illustration.
- URL holds all state (filters, tabs, selected result), so every view can be shared.
- Responsive down to tablet. Read-only views (run detail, comparison) work on mobile.
- Motion: 120–200 ms ease-out. Respect `prefers-reduced-motion`.
- Accessibility: WCAG 2.2 AA, focus rings, meaning never carried by color alone (icon + label).

  | 5 | magenta | `#E87BA4` | `#D55181` |
  | 6 | yellow | `#EDA100` | `#C98500` |

  At most 6 series (beyond that: fold into "Other" or use small multiples). Scatter/bubble charts are capped at 3 series (all-pairs validated).
  Light aqua/magenta/yellow are below 3:1 contrast, so charts using them always ship direct labels or a table view.
- Sequential (magnitude, heatmaps): the single-hue iris ramp 50→900.
- Diverging (score deltas, A-vs-B): **blue `#2A78D6` ← gray midpoint (`#E3E6EB` / `#343945`) → red `#E0383E`**.
  Blue = improvement, red = regression (avoids the red/green CVD trap; arrows ▲▼ also used).

### 12.4 Chart rules (ECharts theme `airval-light` / `airval-dark` generated from tokens)
- Thin marks: 2 px lines, ≥ 8 px markers, 4 px rounded bar ends, 2 px surface gap between adjacent fills.
- One y-axis only, never dual-axis. Recessive gridlines (`--border`), muted axis labels.
- Legend whenever there are ≥ 2 series; direct labels when there are ≤ 4. Text is in text tokens, never series colors.
- Crosshair tooltip on line/area; per-mark tooltip on bar/cell. Every chart has a "View as table" toggle.
- Stat tiles over charts when the job is one headline number.

## 16. Milestones (build order for the one-shot)

Each milestone ends green (`make check`) and demoable.

1. **Foundations.** Repo scaffold, Makefile, config, slog/OTel, store interfaces + both dialects + migrations, embedded NATS,
   `airval dev` boots the SPA shell. Design tokens, UI primitives, app shell (sidebar, ⌘K, theming).
2. **Auth & orgs.** Setup flow, login, sessions, memberships/RBAC, API keys, secrets, settings pages.
3. **Projects & targets.** CRUD, the `http`/`openai`/`anthropic` adapters, test-connection playground, `tools/mocktarget`.
4. **Datasets.** Import (CSV/JSONL/JSON/Parquet/HF), mapping, editor, versions, export.
5. **Evaluators.** Deterministic pack, LLM judge + presets, evaluator editor with live preview.
6. **Suites & runs engine.** Planner, sharding, worker pipeline, AIMD rate limiting, cache, batching, finalizer,
   aggregates, gates, SSE live progress. **Hit the §3.4 benchmarks.**
7. **Run & comparison UI.** Run detail (scorecards, charts, results table, drawer), runs list, comparison, overview trends.
8. **Triggers & CI.** Schedules, webhooks, `airval run` CLI, GitHub Action, notifications.
9. **Multi-turn & agents.** Conversation scripts, user simulator, trace mapping, tool-call evaluators, trace timeline UI.
10. **Human review.** Queues, grading UI, annotations, judge-agreement metrics.
11. **Packaging.** Dockerfile, compose, Helm chart (+ KEDA), goreleaser, install script, docs site (`docs/`, served at `/docs` optional).

13. **Polish.** Sample project, empty states, onboarding wizard, a11y audit, performance pass, e2e coverage of the golden path.

**Definition of done for v1:** a new user installs via any of the three channels, completes onboarding in under 3 minutes with the
sample project, runs a 1,000-example suite against the mock target in **under 15 s**, sees live charts, compares against a
baseline, and gates a CI run via `airval run --gate`.

## 18. Open risks
- **sqlc on two dialects** doubles query files. Mitigation: shared contract tests; keep SQL portable; JSON operations go behind helpers.
- **LLM-judge variance.** Mitigation: N-sample voting, temperature 0, cached results, human calibration.
- **Provider rate limits dominate wall-clock.** Mitigation: AIMD + batch APIs + cache. The UI surfaces "rate-limited x% of time" so users know.
